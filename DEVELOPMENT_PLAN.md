# DEVELOPMENT_PLAN.md

Roadmap de desenvolvimento em 10 fases, com plano detalhado da Fase 1 (próximo ciclo de implementação).

## Visão geral das 10 fases

| Fase | Entregável principal |
|---|---|
| 1. Fundação | Monorepo, infra Docker, banco, autenticação, multiempresa, usuários, permissões, auditoria, arquivos, filas, feature flags, testes fundamentais |
| 2. Painel Master básico | Empresas, planos, módulos, limites, usuários Master, acesso assistido, configurações |
| 3. CRM | Contatos, deduplicação, funis, etapas, oportunidades, tarefas, campos personalizados, busca, relatórios básicos |
| 4. WhatsApp e conversas | Abstração de provedores, números, webhooks, conversas, mensagens, API oficial, conexão não oficial, aceite de risco, templates |
| 5. Atendimento | Caixa de entrada, filas, distribuição, equipes, transferências, horários, WebSocket, resumos |
| 6. Chatbot | Flow Builder, cards, conexões, validações, subfluxos, retorno, execução, integração CRM, IA, base de conhecimento |
| 7. Automação | Gatilhos, condições, ações, filas, agendamentos, follow-ups, logs, tratamento de falha, integração entre módulos |
| 8. Financeiro e afiliados | Contratação, assinatura, cobrança manual, gateways, links de afiliados, comissões, estornos, pagamentos |
| 9. Relatórios e dashboard | Indicadores, filtros, exportações, performance, consolidação |
| 10. Estabilização | Testes E2E, segurança, performance, acessibilidade, documentação, observabilidade, backup, homologação |

Cada fase só é considerada concluída quando os itens de `ACCEPTANCE_CRITERIA.md` são atendidos para tudo o que foi entregue nela. Fases posteriores dependem das entidades e contratos definidos em `DATABASE_DESIGN.md`, `MODULE_DEPENDENCIES.md`, `PERMISSIONS_MATRIX.md` e `SECURITY.md` — qualquer desvio necessário deve atualizar esses documentos antes de seguir.

## Frontend (`apps/web`) — nova frente após as 10 fases do backend

As 10 fases acima cobrem só `apps/api` + `apps/worker` (decisão consciente registrada desde a Fase 6). O frontend ganhou seu próprio roadmap de 9 fases (F1–F9 — F6 foi dividida em duas ao longo do ciclo, ver nota abaixo da tabela), consumindo a API já pronta e testada:

| Fase | Entregável principal |
|---|---|
| F1. Fundação | Cliente HTTP, autenticação, shell do painel adaptável a módulos ativos, dashboard "Início" |
| F2. CRM | Contatos, Kanban de oportunidades, tarefas |
| F3. WhatsApp e Atendimento | Caixa de entrada em tempo real, números, filas |
| F4. Chatbot | Flow Builder visual sobre o motor já existente |
| F5. Automação | Construtor de gatilho/condição/ação, histórico de execuções |
| F6. Financeiro (tenant) | Planos, contratação, faturas, pagamento |
| F7. Relatórios | Telas dos 6 relatórios + exportação CSV |
| F8. Polimento | Responsividade, acessibilidade, estados de loading/vazio/erro |
| F9. Painel Master (Afiliados) | Login/shell Master novo no `apps/web` + gestão de afiliados e comissões |

Nota: a redação original desta tabela incluía "painel Master de afiliados" dentro da F6, mas o painel Master exige uma frente de UI inteiramente nova (autenticação e shell próprios — nada disso existe em `apps/web` até aqui, só o painel do tenant), então foi desmembrada para a F9 antes de a F6 começar, decisão tomada com o usuário no início do ciclo da F6.

## Frontend — Fase F1 — Fundação — STATUS: concluída

Implementado e verificado manualmente ponta a ponta em navegador real (cadastro → sessão → dashboard → logout → guard de rota → sidebar adaptável a módulo ativado via Master), contra `apps/api` real (não mockado).

- **Cliente HTTP** (`lib/api-client.ts`): `fetch` com `credentials: "include"` — os cookies HttpOnly de sessão vivem no domínio da API (porta 3001 em dev), não no do Next.js (porta 3000); a API já libera isso via CORS com `credentials: true` (ver `apps/api/src/main.ts`, configurado desde a Fase 1). `ApiError` tipado carrega `status` e a mensagem real do backend, usado para diferenciar 401 (credenciais inválidas) de 423 (conta bloqueada — Fase 10) nas telas.
- **TanStack Query** (`lib/query-provider.tsx`) como camada de dados — sem re-fetch em retry para erros 401/403 (não adianta tentar de novo sem nova sessão).
- **Autenticação real**: login, cadastro (com campo de confirmação de e-mail e de senha com `paste` bloqueado no client — exigência literal de `SECURITY.md` §1), recuperação de senha (solicitar + confirmar com token). Testado no navegador com o CNPJ colidindo de propósito para confirmar que o erro real da API ("CNPJ já cadastrado.") chega e é exibido, não só o caminho feliz.
- **Endpoint novo no backend**: `GET /tenant-users/me` (sem exigir permissão de "configuracoes" — todo usuário pode ver o próprio nome/e-mail) — não existia porque `/auth/tenant/me` só devolve o payload do JWT (id/tenantId/roleId), sem nome/e-mail para exibir na topbar.
- **Shell do painel adaptável de verdade**: a sidebar só mostra um item de módulo comercial se a `FeatureFlag` do tenant estiver ativa (verificado ativando "crm" via Master API com o app rodando e confirmando que o item aparece sem reload de código) — itens cujo frontend ainda não existe (todos exceto Início nesta fase) ficam visíveis mas desabilitados ("em breve"), nunca escondidos silenciosamente nem linkando para uma tela quebrada.
- **Proteção de rota**: guard client-side (`app/painel/layout.tsx`) — verificado tanto o redirect de `/painel` → `/login` quando deslogado quanto o carregamento normal quando autenticado.
- **Dashboard "Início" real**: consome `GET /reports/dashboard`, mostra só os cartões dos módulos ativos (Financeiro sempre aparece, por não ser módulo comercializável separadamente).
- **Tema claro/escuro** (`lib/theme.tsx`): tokens de cor via CSS custom properties (`--brand-*`, `--ink*`, `--surface*`, `--line`) redefinidos sob a classe `.dark` — os componentes usam sempre os mesmos nomes de classe Tailwind (`bg-surface`, `text-ink`, `border-line`), então nenhuma tela precisa de lógica condicional de tema. Persistido em `localStorage`, com detecção inicial de `prefers-color-scheme` e um script inline (`next/script beforeInteractive`) que aplica a classe antes da primeira pintura — sem isso haveria um flash do tema errado. Verificado em navegador nas telas de auth e no painel: alternância muda cor de fundo/texto/bordas de verdade (não só o botão).
- **Internacionalização** (`lib/i18n/`): pt-BR (padrão), pt-PT, en, es — dicionários tipados (`Record<DictionaryKey, string>`, TypeScript obriga as 4 traduções a terem exatamente as mesmas chaves do dicionário-fonte pt-BR, erro de compilação se uma tradução ficar incompleta). Detecção inicial por `navigator.languages`, com fallback para pt-BR; escolha persistida em `localStorage`, independente do tema. Cobre 100% do que existe até aqui: shell (sidebar/topbar), autenticação (login/cadastro/recuperação de senha) e dashboard. Verificado no navegador com pt-PT usando vocabulário propositalmente diferente do pt-BR ("Contactos"/"Estado" vs. "Contatos"/"Status") para confirmar que não é uma cópia disfarçada.

Débito técnico consciente, registrado deliberadamente (não por omissão): proteção de rota é 100% client-side — não há middleware/SSR autenticado, porque os cookies de sessão pertencem ao domínio da API (porta diferente em dev), não ao do Next.js; isso causa um flash breve de "Carregando…" antes do redirect quando a sessão é inválida. Resolver definitivamente exigiria um proxy de cookies (Next.js Route Handlers espelhando `Set-Cookie` para o domínio do Next.js), o que só se justifica quando SSR autenticado for realmente necessário (ex.: SEO de página pública, que este painel não tem). Validação de formulário é só a mínima via atributos HTML (`required`, `minLength`, `type=email`) — sem uma camada de schema compartilhada com o backend ainda (`packages/validation` continua vazio); a validação autoritativa continua sendo a do backend, cujo erro real é sempre exibido na tela.

## Frontend — Fase F2 — CRM — STATUS: concluída

Implementado e verificado ponta a ponta em navegador real, contra a API real: criar contato → abrir ficha → criar funil → adicionar etapa → criar oportunidade → mover/ganhar → criar tarefa → concluir tarefa — tudo nos dois temas e testado explicitamente em inglês e português de Portugal para garantir que as novas telas também usam `useI18n()` (não strings soltas).

- **Contatos** (`app/painel/crm/contatos/`): lista com busca (`GET /crm/contacts?search=`), criação inline, ficha (`/contatos/[id]`) com edição e a seção de tarefas do contato embutida (`components/crm/contact-tasks.tsx`, reaproveitado também na aba genérica de Tarefas).
- **Funil/Pipeline** (`app/painel/crm/funil/`): bootstrap guiado quando o tenant ainda não tem funil nem etapa (em vez de uma tela quebrada ou vazia); Kanban com colunas por etapa, cartões com valor formatado por locale (`toLocaleString(locale)`), mover etapa via botões (◀/▶ — sem drag-and-drop nesta fase, ver débito abaixo) e fechar como ganha/perdida.
- **Tarefas** (`app/painel/crm/tarefas/`): lista geral com abas de status (pendentes/concluídas/vencidas/todas), criação vinculada a um contato buscado por nome, conclusão em um clique. O nome do contato na tabela é resolvido no cliente (busca a lista de contatos uma vez e cria um mapa id→nome) porque `GET /crm/tasks` não inclui a relação — evitou alterar o contrato da API só para exibição, decisão registrada aqui para não parecer um bug esquecido.
- **Bug real encontrado e corrigido durante a verificação em navegador**: o formulário de novo contato enviava `email: ""` quando o campo ficava em branco, e o DTO do backend (`@IsOptional() @IsEmail()`) só pula a validação quando a chave está *ausente*, não quando é string vazia — resultava em "email must be an email" ao criar um contato sem e-mail. Corrigido com um helper genérico `omitEmptyStrings()` (`lib/api-client.ts`) aplicado em `useCreateContact`/`useUpdateContact`, reutilizável pelos próximos formulários do mesmo tipo.

Débito técnico consciente, registrado deliberadamente: mover oportunidade de etapa é por botão, não drag-and-drop (uma biblioteca de DnD é um investimento maior, melhor introduzir quando o Flow Builder do Chatbot, Fase F4, já justificar essa dependência no projeto de qualquer forma); criação de funil/etapa usa formulários mínimos (sem reordenar etapas, sem cor/probabilidade customizada na tela — a API já suporta, só a UI ainda não expõe).

## Frontend — Fase F3 — WhatsApp e Atendimento — STATUS: concluída

Implementado e verificado ponta a ponta em navegador real, contra a API real: criar número → aceitar termo de risco → conectar (QR simulado) → confirmar conexão → simular mensagem recebida (`POST /whatsapp/conversations/dev/simulate-incoming`, via `fetch` direto — não existe gatilho de UI para esse endpoint dev-only de propósito) → mensagem chega na Inbox em tempo real via WebSocket → assumir conversa → responder → encerrar → reabrir → criar Equipe → criar Fila. Tudo com WebSocket real (`socket.io-client`, mesmo cookie de sessão via `withCredentials`), não polling disfarçado.

- **Números de WhatsApp** (`app/painel/whatsapp/`): lista, criação (tipo agente/chatbot, modalidade oficial/não-oficial), conectar/confirmar/desconectar, aceite de termo de risco obrigatório para modalidade não-oficial.
- **Caixa de entrada** (`app/painel/atendimento/inbox/`): duas colunas (lista de conversas + painel da conversa selecionada), abas por status (abertas/pendentes/encerradas), ações de atendimento (assumir, assumir automático por fila, devolver à fila, transferir, atribuir fila, encerrar/reabrir), envio de mensagem. `RealtimeProvider`/`useRealtimeEvent()` (`lib/realtime.tsx`) escuta `conversation:message` e `conversation:updated` do `RealtimeGateway` do backend — a lista invalida a query da inbox, e o painel aberto anexa a mensagem nova diretamente no cache (sem esperar o próximo poll de 15s).
- **Filas e equipes** (`app/painel/atendimento/equipes/`): CRUD básico de Teams e Queues.
- **Três bugs reais encontrados e corrigidos durante a verificação em navegador** (todos no backend, não na UI que os expôs):
  1. `GET /whatsapp/numbers` (lista e detalhe) nunca devolvia se o termo de risco já tinha sido aceito — o método `hasAcceptedRisk()` existia no service mas nunca era chamado pelos endpoints usados pela tela. Resultado visível: o botão "Aceitar termo de risco" continuava aparecendo (e podia ser clicado de novo) mesmo depois de aceito, sem nenhum jeito de saber pela UI que já tinha sido aceito. Corrigido adicionando `riskAccepted: boolean` à resposta de `list()`/`get()` em `numbers.service.ts`, e a UI agora troca o botão por um indicador estático quando `riskAccepted` é verdadeiro.
  2. `GET /whatsapp/conversations/:id` (usado pelo painel de detalhe da conversa) só incluía `messages` — faltavam os `include` de `queue` e `responsavel` que o endpoint irmão de listagem (`GET /atendimento/inbox`) já tinha. Resultado visível: depois de "Assumir" uma conversa (mutação com sucesso, 201), o painel continuava mostrando "Sem responsável" indefinidamente. Corrigido igualando os `include` dos dois endpoints em `conversations.service.ts`.
  3. Um terceiro problema investigado não era bug de código: o provedor de desenvolvimento da modalidade não-oficial (`FakeUnofficialProvider`) guarda o estado de conexão em um `Map` **em memória**, não no banco — qualquer reinício do processo da API (inclusive o hot-reload do `nest start --watch` ao salvar um arquivo) apaga esse estado, mesmo que a coluna `status` do número no banco continue dizendo "conectado". Isso derrubou o envio de mensagem com "Número não está conectado" no meio da verificação. Não foi corrigido (é uma limitação assumida do simulador dev — comentário já existente no arquivo explica a escolha), só documentado aqui para não ser confundido com regressão em futuras sessões de teste manual: basta desconectar/reconectar o número depois de qualquer reinício do backend.
- Também descoberta durante a investigação do botão "Novo número" (que parecia não responder a cliques no início da sessão): não era bug — era o método de automação do navegador usado na verificação (clique por coordenada em `ref` capturado antes de uma re-renderização) ficando com referência desatualizada. Clique disparado via handler nativo confirmou que o toggle sempre funcionou.

Débito técnico consciente, registrado deliberadamente: tela de Templates da Meta não foi construída (a API já suporta CRUD + submissão/aprovação, Fase 4 do backend); Horários de Atendimento (`BusinessHours`) não têm tela própria ainda (a API já suporta); Filas e Equipes não têm edição/exclusão nem reordenação na UI, só criação e listagem — a API cobre mais do que a tela expõe.

## Frontend — Fase F4 — Chatbot (Flow Builder visual) — STATUS: concluída

Implementado e verificado ponta a ponta contra a API real: criar fluxo (cria automaticamente o nó "início" + versão 1) → abrir o Flow Builder → adicionar cards de mensagem e fim → editar o texto da mensagem (propagado ao vivo no card) → salvar definição → tentar publicar um grafo sem conexões e confirmar que os erros reais do validador do backend aparecem na tela (nó inalcançável, sem saída, ciclo sem saída) → conectar os cards → salvar → publicar com sucesso (fluxo muda para "Publicado" e o editor vira somente leitura) → criar um número de WhatsApp do tipo "chatbot" e vincular o fluxo publicado a ele → criar e desativar um item da Base de Conhecimento.

- **Lista de fluxos** (`app/painel/chatbot/`): criação, e ações de ciclo de vida — publicar, pausar, arquivar, nova versão — espelhando exatamente os endpoints do backend (`/chatbot/flows/:id/publish|pause|archive|new-version`). Erros de validação de publicação (`FlowValidationError[]`) são exibidos com a mensagem real de cada nó problemático, não uma mensagem genérica.
- **Flow Builder visual** (`app/painel/chatbot/fluxos/[id]/`, biblioteca `@xyflow/react`): canvas com os 8 tipos de card (início, mensagem, pergunta, menu, condição, subfluxo, transferir, fim), cada um com handles de conexão específicos — menu gera um handle de saída por opção (`chave` como `sourceHandle`, o mesmo valor que o motor de execução usa para casar a resposta do usuário) e condição gera dois handles fixos (`true`/`false`). Painel lateral de edição por tipo de card (texto, variável, validação, opções de menu, campo/operador/valor da condição, fluxo de destino do subfluxo, fila de transferência). Fluxo publicado vira somente leitura (o backend só aceita `PATCH .../definition` com `status: "draft"`, então a UI reflete essa regra em vez de deixar o usuário editar e descobrir o erro só ao salvar).
- **Base de conhecimento** (`app/painel/chatbot/base-de-conhecimento/`): CRUD simples (criar, listar por tipo, desativar/reativar).
- **Vínculo fluxo↔número de WhatsApp**: seletor de fluxo adicionado à linha do número na tela de WhatsApp (`/painel/whatsapp`) quando `tipo === "chatbot"`, usando o endpoint já existente `PATCH /whatsapp/numbers/:id/chatbot-flow`.
- Diferente das Fases F2/F3, a superfície do Chatbot (`/chatbot/flows/*`, `/chatbot/knowledge-base/*`) respondeu exatamente como documentado — nenhum bug novo de backend encontrado nesta fase.
- **Bug real de frontend encontrado e corrigido durante a verificação**: os handles de conexão do card (`<Handle>` do `@xyflow/react`) tinham `id` explícito (`"in"`/`"out"`) mesmo nos cards onde só existe um handle de cada tipo. Como o contrato `FlowEdge` do backend não carrega `targetHandle` (só `sourceHandle`, usado apenas por menu/condição), uma aresta sem `targetHandle` não conseguia casar com um handle de destino com `id` explícito, e a aresta não era desenhada. Corrigido removendo o `id` dos handles que não precisam de desambiguação (mensagem, pergunta, subfluxo, início/fim) — só menu (por opção) e condição (`true`/`false`) mantêm `id` explícito, que é exatamente o que o motor de execução espera.
- **Limitação de ambiente de teste, não bug de produto**: a verificação de "arrastar para conectar dois cards" não pôde ser confirmada visualmente nesta sessão porque o navegador usado pela automação de testes não executa ciclos de pintura/composição (`ResizeObserver` nunca dispara nesse ambiente, confirmado com um teste direto), e o `@xyflow/react` depende de `ResizeObserver` para medir os cards antes de desenhar as arestas. A cadeia de dados foi verificada de ponta a ponta por outra via: arestas gravadas diretamente via API, confirmadas no estado React do editor (idênticas ao que o backend armazenou) e a publicação subsequente foi aceita pelo validador do backend — prova de que o problema é exclusivamente de renderização visual neste ambiente de automação, não da lógica da aplicação.
- **Descoberta registrada, não corrigida (comportamento do backend, não da tela)**: `GET /chatbot/knowledge-base` sempre filtra `ativo: true`, então um item desativado desaparece da lista e o botão "Reativar" fica inacessível pela UI (só reapareceria com filtro OU com uma consulta por id direta). Documentado aqui para não ser confundido com bug do frontend em sessões futuras.

Débito técnico consciente, registrado deliberadamente: sem drag-and-drop de novos cards a partir de uma paleta (o botão "+ Adicionar cartão" insere o card em cascata e o usuário arrasta para reposicionar); sem atalho de teclado para excluir múltiplos cards; a tela não expõe `aiEnabled` do fluxo nem os tipos de card `ai`/`knowledge_query` (o próprio backend os rejeita na validação de publicação, por não terem motor de execução ainda — ver `flow-definition.types.ts`).

## Frontend — Fase F5 — Automação — STATUS: concluída

Implementado e verificado ponta a ponta contra a API e o motor de automação reais: criar uma automação (gatilho "Mensagem recebida", uma condição, uma ação de aplicar etiqueta) → editar (remover a condição, salvar) → disparar o evento de verdade (`POST /whatsapp/conversations/dev/simulate-incoming`, o mesmo endpoint dev usado nas Fases F3/F4) → confirmar que o `AutomationEngineService` casou a regra, criou e processou a `AutomationExecution` de verdade via a fila BullMQ real (não simulada) → ver a execução com status "Sucesso" na tela de histórico.

- **Lista e CRUD de automações** (`app/painel/automacao/`): criar, editar (nome, descrição, gatilho, condições, ações), pausar/ativar/arquivar. O seletor de gatilho é populado a partir da mesma lista de 13 eventos de domínio que o backend aceita (`@IsIn(ALL_DOMAIN_EVENTS)`), então não há como a tela oferecer um gatilho que a API rejeitaria.
- **Editor de condições** (`conditions-editor.tsx`): lista de condições campo/operador/valor, todas combinadas com E — o campo de valor só aparece para os operadores `equals`/`contains` (para `exists`/`not_exists` o backend ignora `valor`, então a tela não pede um valor que não seria usado).
- **Editor de ações** (`action-fields.tsx`): os 9 tipos de ação reais do motor (`send_message`, `create_task`, `apply_tag`, `remove_tag`, `update_field`, `move_opportunity_stage`, `start_chatbot`, `send_webhook`, `schedule_followup`), cada um com os campos específicos que o `AutomationProcessor` de fato consome — inclusive o seletor de fluxo em "Iniciar fluxo do chatbot" reaproveita `useFlows()` da Fase F4.
- **Histórico de execuções** (`app/painel/automacao/[id]/execucoes/`): status, gatilho disparado, tentativas, erro (quando houver) e data — consumindo `GET /automation/rules/:id/executions` diretamente, sem endpoint novo no backend.
- Nenhum bug de backend nem de frontend encontrado nesta fase — o contrato respondeu exatamente como documentado, incluindo o comportamento "silencioso" já esperado de uma ação que depende de `contactId` quando a conversa simulada não tem contato vinculado (`{ skipped: "sem contactId" }`, gravado em `acoesExecutadas` e a execução ainda assim marcada "success", porque a ação não lançou erro — comportamento do motor, não da tela).

Débito técnico consciente, registrado deliberadamente: a tela não expõe `FollowUpSchedule` (não há endpoint público para isso — é inteiramente interno, criado/cancelado pelo próprio motor); não há um "testar automação" (disparar manualmente sem esperar o evento real) nem visualização amigável de `acoesExecutadas` (a tela de execuções não mostra o JSON do resultado de cada ação, só o resumo status/tentativas/erro) — a API já devolve o dado, só a UI ainda não o exibe.

## Frontend — Fase F6 — Financeiro (tenant) — STATUS: concluída

Antes de começar, duas lacunas reais no contrato foram levantadas com o usuário (não presumidas): o backend não tinha endpoint para o tenant listar os planos disponíveis (só "assinar plano por ID"), e o roadmap original desta fase incluía um painel Master de afiliados que exigiria construir autenticação e shell Master do zero em `apps/web` — nada disso existe ainda, só o painel do tenant. Decisão tomada com o usuário: (1) adicionar o endpoint de listagem de planos ao backend, já testado; (2) mover o painel Master/Afiliados para uma fase própria (F9), fechando esta fase só com o Financeiro do tenant.

Implementado e verificado ponta a ponta contra a API e o gateway de pagamento simulado reais: abrir a tela sem assinatura → ver os planos disponíveis (com preço e recorrência formatados) → contratar um plano real → a assinatura aparece em "Aguardando pagamento" e a primeira fatura em "Pendente" → pagar a fatura com cartão → a assinatura vira "Ativa" e a fatura vira "Paga" com a data e o método corretos.

- **Endpoint novo no backend**: `GET /billing/plans` (`apps/api/src/billing/billing.controller.ts`, mesma permissão `configuracoes:view` dos demais endpoints de billing do tenant) — devolve só os planos com `ativo: true`, ordenados por preço. Coberto por um teste de integração novo (`billing-affiliates.spec.ts`, confirma que um plano desativado pelo Master some da lista do tenant) — suíte completa (4 testes) passando contra Postgres real.
- **Tela de Financeiro** (`app/painel/financeiro/`): estado da assinatura atual (reaproveita as chaves de tradução `dashboard.financeiro.status.*` que já existiam desde a Fase 1, para não duplicar rótulos de status entre o dashboard e esta tela), grade de planos disponíveis com o plano atual destacado e desabilitado, lista de faturas com seletor de forma de pagamento (Pix/Boleto/Cartão) e botão de pagar — visível só em faturas pendentes/vencidas, exatamente a regra que o backend aplica (`invoice.status !== "pending" && !== "overdue"` → 400).

## Frontend — Fase F8 — Polimento — STATUS: concluída

Diferente das fases anteriores, esta foi uma auditoria e correção sobre as telas já construídas (F1–F7), não uma tela nova. Verificado em navegador nas larguras mobile (375px), tablet (768px) e desktop (1280px), sempre contra a API real.

- **Responsividade — o gap real**: a sidebar era `w-60` fixo e sempre visível, sem nenhum comportamento para telas estreitas — em 375px ela sozinha já ocupava 64% da largura da tela. Corrigido com um menu tipo gaveta: `Sidebar` agora recebe `open`/`onClose`, fica fora da tela (`-translate-x-full`) em telas `&lt;md`, e a `Topbar` ganhou um botão de hambúrguer (`md:hidden`) para abri-la, com um backdrop que fecha ao clicar fora e fecha automaticamente ao navegar. A partir de `md` (768px) o comportamento antigo é preservado (sidebar sempre visível, sem hambúrguer) — verificado que a mudança de breakpoint não quebra o desktop.
- **Caixa de entrada do Atendimento**: o layout de duas colunas (lista + conversa) ficava lado a lado sempre, mesmo em telas onde nenhuma das duas cabia de forma legível. Corrigido para empilhar em mobile (`flex-col md:flex-row`) e alternar entre lista e conversa conforme a seleção (`selectedId`), com um botão de voltar (`←`, visível só em mobile) no cabeçalho da conversa — testado nas duas direções (abrir conversa esconde a lista, voltar reexibe a lista) sem afetar o layout lado a lado do desktop.
- **Tabelas e grades de formulário**: as 8 tabelas do painel (WhatsApp, CRM, Chatbot, Automação, Financeiro, Relatórios) ganharam `overflow-x-auto` no contêiner em vez de `overflow-hidden`, para rolar horizontalmente em vez de espremer colunas até ficarem ilegíveis; as ~17 grades de formulário com `grid-cols-2`/`grid-cols-3` fixos (nome/e-mail, tipo/modalidade/número, etc.) passaram a empilhar em uma coluna abaixo do breakpoint `sm`, revertendo ao layout original em telas maiores.
- **Acessibilidade**: 3 botões de remover (ícone "×", em condições de automação, ações de automação e opções de menu do chatbot) não tinham rótulo acessível — adicionada `aria-label` (chave `common.remove`, nova nas 4 dicionárias) a todos. O atributo `lang` do `&lt;html&gt;` ficava fixo em `pt-BR` mesmo quando o usuário trocava de idioma — como a troca de idioma é 100% client-side (a mesma razão pela qual o tema precisa de um efeito para alternar a classe `dark`), corrigido com um `useEffect` em `I18nProvider` que atualiza `document.documentElement.lang` a cada troca de locale. Os overlays de fechar menu (idioma, usuário, sidebar mobile) ganharam `aria-hidden="true"` para consistência. Focus-visible, contraste e navegação por teclado já estavam corretos desde a Fase F1.5 (tokens de tema) — nenhum ajuste necessário ali.
- **Bug real de estado de carregamento encontrado e corrigido**: a tela de Financeiro mostrava "Você ainda não tem uma assinatura ativa" enquanto a consulta de assinatura ainda estava carregando (`subscription.data` é `undefined` tanto durante o carregamento quanto quando de fato não há assinatura — a tela não distinguia os dois casos), o que podia piscar uma informação errada por um instante antes do dado real chegar. Corrigido adicionando o estado de carregamento explícito (`subscription.isLoading`) antes do branch vazio.

Débito técnico consciente, registrado deliberadamente: sem auditoria de contraste com ferramenta automatizada (WCAG AA) — os tokens de cor foram desenhados com contraste em mente na Fase F1.5, mas não houve verificação numérica formal; Kanban do CRM e o canvas do Flow Builder do Chatbot continuam exigindo rolagem horizontal em mobile por natureza (grade de colunas e editor de grafo, respectivamente — não há como empilhar verticalmente sem perder a metáfora visual).

## Fase 10 — Estabilização — STATUS: concluída

Última fase do roadmap. Implementado e testado (69 testes automatizados no total — 66 em `apps/api` + 3 em `apps/worker`, o primeiro teste automatizado do worker desde que ele existe). Escopo escolhido deliberadamente a partir dos débitos técnicos **explicitamente registrados como pendentes para esta fase** em ciclos anteriores (ver §156 e a nota de Fase 1), priorizando o que é seguro e testável de implementar de verdade agora, em vez de itens vagos de "polimento" sem critério de aceite claro:

- **Bloqueio progressivo por conta** (`account-lockout.util.ts`): a partir da 5ª tentativa de login falha seguida, a conta trava por um tempo que dobra a cada nova falha (1min → 2 → 4 → ... até 60min); reseta no login correto. Aplicado a `TenantUser` e `MasterUser`. Complementa (não substitui) o rate limit por IP/rota já existente — testado explicitamente sem tocar no `MasterUser` semeado usado por toda a suíte (um `MasterUser` descartável é criado só para o teste de bloqueio, evitando travar os outros 65 testes que dependem do login Master funcionando).
- **Envio real de e-mail** (boas-vindas e recuperação de senha): fecha o TODO literal que existia em `auth.service.ts` desde a Fase 1 — a recuperação de senha **gerava o token e o descartava**, tornando o fluxo inutilizável de ponta a ponta. Agora enfileira de verdade na fila `notifications` (BullMQ); `apps/worker` processa com uma abstração `EmailProvider` (mesmo padrão do `WhatsAppProvider`/`PaymentProvider`) implementada por um `LogEmailProvider` simulador — sem credenciais reais de SMTP/API de e-mail disponíveis neste ambiente, mesma situação do Meta/gateway de pagamento. Cada "envio" gera um `EmailLog` real e consultável (não um log solto): a auditoria (`notification.welcome_sent`/`notification.password_reset_sent`) e o teste ponta a ponta usam esse registro como prova.
- **Primeira suíte de testes do `apps/worker`**: até esta fase, a fila "notifications" nunca tinha sido verificada por um teste automatizado — só manualmente. Adicionado `jest`/`ts-jest`/`@nestjs/testing` ao worker e um teste real que enfileira na fila de verdade (mesmo Redis) e confirma que o `NotificationsProcessor`, rodando como um worker de verdade, consome e persiste o resultado.
- **Revisão completa de `SECURITY.md`**: cada item do checklist revisado e marcado como implementado/testado ou registrado como débito técnico consciente com justificativa (ver `SECURITY.md` §10) — não deixado como pendência implícita.

Débito técnico consciente, registrado deliberadamente como backlog pós-lançamento (decisão de custo/benefício, não omissão — ver justificativa completa em `SECURITY.md` §10): **Row-Level Security do Postgres** (isolamento por `tenantId` já é reforçado e testado em toda a camada de aplicação; adicionar RLS exigiria propagar `tenantId` como variável de sessão Postgres por requisição, mudança arquitetural ampla que malfeita é pior que a situação atual — merece um ciclo dedicado, não um item de fechamento de fase); resolução de tenant por subdomínio (sem frontend multi-tenant real ainda, não há consumidor prático); TLS/backup de produção (dependem da infraestrutura de deploy real, fora do escopo de ambiente de desenvolvimento local); exportação/exclusão de dados pessoais sob demanda (LGPD) — soft delete já preserva histórico, mas falta um endpoint dedicado.

**Frontend (`apps/web`) não foi implementado em nenhuma fase deste ciclo** — por decisão explícita registrada nas Fases 6 e 8 (Flow Builder visual e portal de autoatendimento do afiliado ambos adiados "para um ciclo dedicado a frontend"), todo o desenvolvimento das 10 fases cobriu o backend (`apps/api` + `apps/worker`) de ponta a ponta, com testes de integração reais contra Postgres/Redis/MinIO — não telas. Isso é consistente do início ao fim do projeto, não uma surpresa desta fase final.

## Fase 11 — Integração com IA (Claude, ChatGPT, Gemini) — STATUS: concluída

Primeira fase de um novo ciclo, aberto depois que o roadmap original (backend 10 fases + frontend F1–F9) foi concluído. Escopo combinado com o usuário: modelo híbrido de chave (o tenant pode usar a própria chave de API — BYOK — e/ou a chave da própria plataforma, liberado individualmente pelo Master por empresa), aplicado primeiro aos cards "IA" e "Consulta à Base" do Flow Builder do Chatbot — que já existiam no motor mas eram sempre rejeitados na validação de publicação por falta de motor de execução (ver `flow-definition.types.ts`, `UNSUPPORTED_TYPES`, desde a Fase 6). Busca semântica com embeddings/RAG completo e um assistente de IA dentro do CRM/Atendimento ficaram fora desta rodada, por decisão do usuário — a "Consulta à Base" usa correspondência por palavra-chave como contexto, não vetores.

Backend e frontend tocados na mesma fase (não dividida em duas, diferente do padrão F1–F9, porque a mudança é pequena o suficiente para caber num único ciclo coerente):

- **Abstração `AiProvider`** (`apps/api/src/ai/providers/`) — mesmo padrão já usado três vezes no projeto (`WhatsAppProvider`, `PaymentProvider`): uma interface única (`complete({apiKey, systemPrompt?, messages})`) implementada por três adaptadores reais via `fetch` nativo (sem SDK novo) — `AnthropicProvider` (Claude, Messages API), `OpenAiProvider` (ChatGPT, Chat Completions) e `GoogleGeminiProvider` (Gemini, generateContent) — mais um `AiProviderRegistryService` que resolve por nome, igual ao `ProviderRegistryService` do WhatsApp.
- **`AiAccessService`** — o "cérebro" da decisão de qual chave usar: lê o `FeatureFlag` (`module: "ia"`, reaproveitando o campo `config Json?` que já existia no schema para módulos comerciais, sem migration nova para isso) e resolve, nesta ordem, (1) a chave própria do tenant se `allowByok` e ela existir, (2) a chave da plataforma (env var por provedor) se `allowPlatformKey` e ela estiver configurada, (3) nega com `ForbiddenException` — nunca finge uma resposta.
- **Armazenamento seguro da chave do tenant (BYOK)**: novo utilitário `secret-encryption.util.ts` (AES-256-GCM, `ENCRYPTION_KEY` de 32 bytes em base64) — primeira criptografia reversível do projeto (`crypto.util.ts` só tinha hash de senha/token, ambos irreversíveis por design, insuficientes aqui porque a chave precisa ser recuperada em texto puro para ser enviada ao provedor). Novo model `TenantAiCredential` (`tenantId`+`provider` único); a chave nunca é devolvida em texto puro por nenhum endpoint, só um booleano "chave cadastrada".
- **Motor do Chatbot**: dois novos `case` em `ChatbotEngineService.advance()` — `"ai"` chama o provedor resolvido com o prompt do card (com substituição de `{{variavel}}` pelas respostas já coletadas no fluxo) e envia a resposta como mensagem; `"knowledge_query"` primeiro busca os 3 itens da Base de Conhecimento mais relevantes por pontuação de palavras-chave (não embeddings), monta um `systemPrompt` com esse contexto e delega para o mesmo caminho do `"ai"`. Se `AiAccessService` negar (sem chave disponível), o card transfere a conversa para um atendente humano — mesmo padrão já usado quando as tentativas de uma pergunta se esgotam — em vez de travar o fluxo ou fingir uma resposta.
- **Validação de publicação**: `flows.service.ts` passou a checar, antes de `validateFlowDefinition` (que continua puramente estrutural), se o fluxo contém nós de IA sem `aiEnabled: true` — campo que já existia no schema (aceito por `create-flow.dto.ts` desde a Fase 6) mas nunca era checado nem exposto na UI até agora.
- **Master**: reaproveitado o endpoint que já existia, `PATCH /master/tenants/:id/modules` — `ToggleModuleDto` ganhou um campo `config` opcional (`{allowByok, allowPlatformKey}`), sem endpoint novo. Nova seção "Inteligência Artificial" em `app/master/painel/empresas/[id]/page.tsx`: toggle de módulo + dois checkboxes.
- **Tenant**: nova área "Configurações" no painel (`app/painel/configuracoes/ia/`) — o módulo `"configuracoes"` já existia no RBAC desde a Fundação mas nunca teve uma tela; o item de navegação já existia desabilitado ("em breve") desde a F1, só precisou trocar `builtInPhase: false` para `true`. Uma seção por provedor mostrando se a chave própria e/ou da plataforma estão liberadas, campo para colar a própria chave (só quando `allowByok`), e status ("usando sua própria chave"/"usando a chave da plataforma"/"não liberado"/"nenhuma chave disponível").
- **Flow Builder**: `aiEnabled` exposto no formulário de criação de fluxo (débito registrado desde a F4, fechado agora); cards "IA"/"Consulta à Base" na paleta e no `NodeInspector` (seletor de provedor populado por `/ai/access`, só mostrando provedores realmente utilizáveis; textarea de prompt; campo de variável).
- **Testes**: `secret-encryption.util.spec.ts` (round-trip, adulteração do payload falha a autenticação, chave errada falha, chave mal formada rejeitada) e `test/ai.spec.ts` — 12 testes de integração cobrindo negação sem módulo habilitado, ciclo completo de cadastro/remoção de BYOK, rejeição de BYOK sem permissão, ausência de chave da plataforma neste ambiente, rejeição de publicação sem `aiEnabled`, transferência para humano quando não há chave disponível (via `POST /whatsapp/conversations/dev/simulate-incoming`, mesmo endpoint dev das fases anteriores), e isolamento entre tenants. Suíte completa do backend: 79/79 passando.
- **Verificação em navegador**: Master habilitou IA (BYOK) para uma empresa de teste real → login como aquela empresa → tela Configurações → cadastrar uma chave (`sk-ant-test-...`) → status mudou para "usando sua própria chave" → criar fluxo com "Habilitar IA" marcado → adicionar card "IA" → seletor de provedor mostrou Claude corretamente sem o aviso de "nenhum provedor disponível". Chamar um provedor real de verdade (Claude/ChatGPT/Gemini respondendo de fato) exige uma API key real, que não está disponível neste ambiente de desenvolvimento — mesma situação já registrada para Meta/gateway de pagamento em fases anteriores; o caminho de erro (sem chave → transferência para humano) foi verificado tanto no teste automatizado quanto é o mesmo código que atende o caminho de sucesso.

Débito técnico consciente, registrado deliberadamente: sem histórico de conversa multi-turno no card de IA (cada chamada é isolada — prompt + contexto opcional, não uma conversa contínua com o provedor); "Consulta à Base" usa pontuação por palavra-chave, não embeddings/busca semântica (decisão explícita do usuário para esta rodada); sem assistente de IA dentro do CRM/Atendimento (também fora do escopo combinado); Master não tem tela para configurar as chaves da própria plataforma — ficam em variáveis de ambiente (`AI_PLATFORM_*_API_KEY`), mesmo padrão já usado para `META_ACCESS_TOKEN`/`PAYMENT_GATEWAY_API_KEY`, não uma limitação nova.

## Fase 12 — Acesso assistido: interface + bug real corrigido — STATUS: concluída

Segundo item da fila de débitos técnicos priorizada por impacto (depois de IA). O endpoint de impersonação (`POST /master/tenants/:id/impersonate`) já existia desde a Fase 2 do backend, testado e funcional — só faltava um botão. ## Fase 14 — Clawback de comissão de afiliado — STATUS: concluída

Quarto item da fila de débitos por impacto. Débito registrado desde a Fase 8: `AffiliatesService.reverseConversion()` só tratava o caso de uma indicação ainda `pending` ser estornada (vira `reversed`, nunca chega a ser paga); se a comissão já tivesse sido paga ao afiliado antes do estorno tardio, nada acontecia — o afiliado ficava com um pagamento que a plataforma nunca recuperava.

- **Backend**: `reverseConversion(tenantId)` passou a considerar a indicação mais recente de `subscription`/`renewal` com status `pending` **ou** `paid` (antes só `pending`). Se já estava `paid`, vira `clawback` (novo valor de string — `AffiliateReferral.status` já era uma coluna `String` livre, sem migration nova) em vez de `reversed`: uma dívida do afiliado com a plataforma, nunca cobrada ativamente, só deduzida do próximo lote de pagamento. `payEligibleReferrals()` agora calcula `netTotal = grossEligible - clawbackTotal` (soma das indicações `clawback` em aberto do afiliado), rejeita com 400 se `netTotal <= 0` ("saldo líquido zerado ou negativo, nada a pagar"), e num pagamento bem-sucedido marca as indicações elegíveis como `paid` **e** os clawbacks em aberto como `clawback_settled` no mesmo lote — resposta inclui `clawbackDeduzido` para a UI explicar a diferença entre bruto e líquido.
- **Frontend**: `master/painel/afiliados/[id]/page.tsx` — o resultado de "Pagar indicações elegíveis" agora mostra uma nota extra quando `clawbackDeduzido > 0` explicando o desconto; e o antigo `catch` silencioso da chamada (erro de rede/negócio não aparecia em lugar nenhum) virou um `<Alert tone="error">` visível — bug de UI encontrado e corrigido durante a própria verificação em navegador desta fase, não relacionado à lógica de clawback em si.
- **Descoberta de infraestrutura de teste** (não um bug de produto): ao adicionar o teste de clawback em `billing-affiliates.spec.ts` (arquivo já grande, reaproveitando seus helpers), a suíte passou a falhar com `429 ThrottlerException` — não por *rate limit* real entre execuções, mas porque `@Throttle({limit:5, ttl:60_000})` em `POST /auth/tenant/signup` é armazenado por instância da aplicação Nest, e cada arquivo de teste sobe a sua própria (`Test.createTestingModule` em `beforeAll`); o arquivo já somava 7 chamadas de `signupTenant()` dentro da sua própria janela de execução, ultrapassando o limite mesmo com Docker saudável e nenhuma outra suíte rodando em paralelo. Corrigido extraindo os dois testes de clawback para um arquivo próprio, `test/affiliate-clawback.spec.ts` (2 chamadas de signup, instância de app própria) — consistente com a convenção já existente no projeto de um arquivo de teste por área de funcionalidade, não uma exceção criada para contornar o problema.
- **Testes**: `affiliate-clawback.spec.ts` — ciclo completo (comissão paga → estorno tardio → vira `clawback` → tentativa de pagamento com líquido zerado é rejeitada e o clawback continua em aberto → nova conversão soma líquido positivo → pagamento dedu o clawback automaticamente e marca `clawback_settled`) e um teste de isolamento (estorno em um tenant de um afiliado não afeta indicações de outro afiliado). Suíte completa do backend: 15 arquivos, 82/82 passando.
- **Verificado em navegador de ponta a ponta**: pagamento elegível normal (sem clawback) mostra só o total, sem nota extra; após um estorno tardio via API do Master, a tabela de indicações do afiliado passa a mostrar o registro como `clawback`; nova tentativa de pagamento com líquido zerado mostra o alerta de erro vermelho "Nenhuma comissão elegível para pagamento no momento." (confirmando o fix do `catch` silencioso); duas novas conversões pagas + nova tentativa de pagamento mostram "2 indicação(ões) paga(s), total de R$ 15.00" com a nota "Inclui R$ 15.00 deduzidos de estorno(s) tardio(s) já compensado(s) neste pagamento." e o registro de clawback muda para `clawback_settled` na tabela.

Débito técnico consciente, registrado deliberadamente: o clawback nunca é cobrado ativamente do afiliado (sem fatura, sem notificação, sem bloqueio) — só reduz o próximo pagamento; se o afiliado nunca mais gerar comissão elegível, a dívida fica em aberto indefinidamente. Implementar cobrança ativa exigiria decidir uma política de negócio (prazo, notificação, o que fazer se o afiliado for desativado com clawback pendente) que não foi definida pelo usuário nesta rodada.

## Fase 17 — Gateway de pagamento real (Stripe) — STATUS: concluída

Último item da fila de débitos por impacto — deixado propositalmente para o final por pedido explícito do usuário ("deixa gateway de pagamento por último"). Até aqui só existia o `FakeGatewayProvider` (Fase 8), um simulador sem nenhuma credencial real.

- **`StripeProvider`** (`apps/api/src/billing/providers/stripe.provider.ts`) — mesmo padrão do resto do projeto (`MetaOfficialProvider`, provedores de IA): `fetch` nativo, sem SDK novo. Diferente do simulador, **nenhum método confirma pagamento de forma síncrona** — cartão, Pix e boleto passam todos pelo Stripe Checkout (sessão hospedada, o tenant é redirecionado para uma página do próprio Stripe) porque esta plataforma não tem Stripe.js/Elements no frontend para coletar dados de cartão com segurança; a confirmação chega depois via webhook. Isso generaliza exatamente a nota que o `FakeGatewayProvider` já deixava desde a Fase 8 ("a confirmação de boleto chegaria depois via webhook do gateway, fora do escopo simulável aqui") — agora implementada de verdade, para todos os métodos.
- **`ChargeResult`** ganhou um campo opcional `checkoutUrl` (interface `PaymentProvider` em `payment-provider.interface.ts`) — não persistido no banco (é efêmero, expira do lado do gateway), só repassado na resposta de `POST /billing/invoices/:id/pay` para o frontend redirecionar.
- **Webhook** (`apps/api/src/billing/webhooks/billing-webhooks.controller.ts`, `POST /billing/webhooks/stripe`) — endpoint público (sem `TenantAuthGuard`, é o Stripe quem chama), mesmo padrão do webhook da Meta: a fatura nunca é resolvida por um campo livre do corpo, e sim pelo `gatewayRef` (id da sessão de checkout) já gravado quando o pagamento foi iniciado. `stripe-signature.util.ts` verifica a assinatura HMAC-SHA256 no formato próprio do Stripe (`t=<timestamp>,v1=<hmac>`), com `timingSafeEqual` (mesma técnica do `MetaOfficialProvider.verifyWebhookSignature`) e checagem de janela de tolerância (5 min) contra replay. `BillingService.confirmPaymentByGatewayRef` é idempotente — um evento duplicado do gateway (comum em produção, o Stripe reenvia até confirmar 200) não reprocessa nem duplica efeito.
- **Seleção de provedor por env**: `payment-providers.module.ts` passou de um único provider fixo (`FakeGatewayProvider`) para um factory que lê `PAYMENT_GATEWAY_PROVIDER` (`fake` por padrão, `stripe` para ligar o real) — troca sem mudar nenhuma linha de `BillingService`, que só fala com a interface `PaymentProvider`. `.env.example`/`.env`: `PAYMENT_GATEWAY_API_KEY` (nunca usado de fato) virou `PAYMENT_GATEWAY_PROVIDER` + `STRIPE_SECRET_KEY` + `STRIPE_WEBHOOK_SECRET`.
- **Frontend**: `usePayInvoice` (`lib/billing.ts`) e a tela Financeiro passaram a checar se a resposta do pagamento traz `checkoutUrl` — quando traz (gateway real), redireciona (`window.location.href`) para a página hospedada do Stripe em vez de só invalidar o cache; quando não traz (simulador), comportamento idêntico ao de antes.
- **Testes**: `stripe-signature.util.spec.ts` (assinatura válida, corpo adulterado, segredo errado, replay fora da janela, header ausente/malformado) e `test/billing-stripe.spec.ts` — arquivo dedicado com `PAYMENT_GATEWAY_PROVIDER=stripe` setado antes de compilar o módulo de teste (assim o factory resolve o Stripe só nesse arquivo, sem afetar os outros) e `global.fetch` mockado para as chamadas a `api.stripe.com`. Cobre: criação de sessão de checkout deixando a fatura `pending` com `checkoutUrl`; webhook com assinatura inválida rejeitado (401) sem alterar a fatura; webhook válido confirmando o pagamento (fatura `paid`, assinatura `active`, evento de domínio); reenvio idempotente do mesmo evento; e estorno via Stripe (busca o `payment_intent` da sessão, depois chama `/v1/refunds`). Suíte completa do backend: 17 arquivos, 91/91 passando — incluindo confirmação de que o `FakeGatewayProvider` continua sendo o padrão e seu comportamento não mudou.
- **Descoberta durante o desenvolvimento do teste** (não um bug de produto): a primeira versão do teste usava um `gatewayRef` mockado fixo (`"cs_test_abc123"`) em vez de um valor único por execução — como o Postgres deste ambiente de desenvolvimento persiste dados entre rodadas de teste, `confirmPaymentByGatewayRef` (que busca por `gatewayRef` sem mais nenhum filtro, correto em produção porque sessões do Stripe são globalmente únicas) acabava batendo com uma fatura de uma execução anterior já paga, fazendo o teste falhar de forma não determinística (passava isolado, falhava junto com o segundo teste do mesmo arquivo). Corrigido gerando um `gatewayRef` único (`cs_test_${randomUUID()}`) por execução — o código de produção não tinha (nem tem) esse problema.
- **Verificado em navegador**: como não há credencial real do Stripe disponível neste ambiente (mesma situação já registrada para a API oficial da Meta e para os provedores de IA), o servidor de desenvolvimento continua rodando com `PAYMENT_GATEWAY_PROVIDER=fake` — confirmado que uma contratação + pagamento via cartão pelo simulador continua funcionando exatamente como antes (fatura paga na hora, sem `checkoutUrl`, sem nenhuma mudança de comportamento visível). O caminho real do Stripe (criação de sessão, webhook, idempotência, estorno) foi verificado de ponta a ponta pelos testes de integração com `fetch` mockado, que é a única forma de exercitar esse código sem uma chave de API real.

Débito técnico consciente, registrado deliberadamente: sem retry automático se o tenant fechar a aba do Checkout sem completar o pagamento (a fatura fica `pending` indefinidamente até o tenant tentar pagar de novo, gerando uma nova sessão — não há lembrete nem expiração ativa); só Stripe como gateway real (Mercado Pago/PagSeguro ficam para quando houver necessidade de negócio concreta, a interface `PaymentProvider` já comporta um novo adaptador sem mudar `BillingService`); sem Stripe Connect/split de pagamento (não faz parte do modelo desta plataforma, que cobra o tenant diretamente, não intermedia pagamentos entre terceiros).

Com esta fase, a fila de débitos técnicos priorizada com o usuário no início deste ciclo (Fases 11–17) está completa.

## Fase 19 — Row-Level Security do Postgres — STATUS: parcialmente concluída (infraestrutura pronta, não ligada em runtime)

Item mais arriscado da lista — decisão consciente de fazer a parte segura (schema/políticas/prova) sem arriscar quebrar isolamento de dados de toda a aplicação numa mudança apressada.

- **Descoberta importante**: a aplicação conecta ao Postgres como o papel `postgres` — dono das tabelas. Postgres nunca aplica RLS ao dono de uma tabela nem a superusuários, por design; só habilitar RLS não teria efeito algum na conexão atual. A migration `20260730010000_add_row_level_security` cria um segundo papel, `app_runtime`, sem privilégios de dono, sujeito às políticas.
- **Política** em 30 tabelas com `tenantId` (todas as tabelas de módulo comercial + auditoria/tokens/e-mail): linha visível/gravável se `tenantId IS NULL` (linhas de sistema), OU `tenantId` bate com a variável de sessão `app.tenant_id` (fluxo de tenant autenticado), OU a variável `app.role = 'master'` (Painel Master/jobs de sistema, que legitimamente cruzam tenants — já autorizados na camada de aplicação).
- **Prova em teste dedicado** (`test/row-level-security.spec.ts`) — não sobe a aplicação NestJS, conecta direto duas vezes no Postgres (uma vez como dono, só para semear dados; outra como `app_runtime`) e comprova: sem variável de sessão, zero linhas visíveis mesmo sem `WHERE`; com `app.tenant_id`, só as linhas do próprio tenant aparecem mesmo numa consulta sem filtro nenhum; um `UPDATE` tentando alterar a linha de outro tenant afeta zero linhas; com `app.role = 'master'`, todos os tenants aparecem. 5/5 testes passando.
- **Débito consciente, registrado deliberadamente (o motivo de não ligar em runtime agora)**: fazer o `PrismaService` de fato usar `DATABASE_RUNTIME_URL` (o papel restrito) exige envolver **toda** chamada ao Prisma no backend numa transação que primeiro roda `SELECT set_config('app.tenant_id', ...)` — um refactor que toca dezenas de serviços, incluindo muitos que hoje usam `PrismaService` bruto com `tenantId` explícito no `where` (Billing, Automação, motor do Chatbot, tudo do Master). Fazer esse refactor errado quebraria isolamento de dados silenciosamente — exatamente o oposto do que RLS existe para proteger. Fica documentado como o próximo passo concreto (a infraestrutura — role, políticas, `DATABASE_RUNTIME_URL` — já está pronta e testada) em vez de arriscado numa mudança apressada em massa.

Quirk de ambiente de desenvolvimento descoberto durante a verificação (não é um bug de produto): o dev server da API (`nest start --watch`, deixado rodando em background ao longo da sessão) e a instância Nest que cada arquivo de teste sobe para si mesmo compartilham a mesma fila BullMQ real no Redis (`automations`) — os dois processos ficam conectados como workers do mesmo nome de fila. Quando o dev server está de pé durante um teste, ele pode "vencer" a corrida e pegar um job enfileirado pelo teste antes do worker do próprio teste, processando-o com `fetch` real (não o `jest.fn()` mockado dentro do processo de teste) e/ou contra dados já limpos pelo `afterAll` de execuções anteriores — causando falhas de `waitFor` por timeout, difíceis de depurar porque a suíte roda "sozinha" sem erro aparente no próprio arquivo. Mitigação: parar o dev server da API antes de rodar testes que envolvam o motor de Automação (`automation*.spec.ts`), e nunca deixá-lo de pé por várias horas durante uma sessão de testes longa sem reiniciá-lo. Armadilha adicional descoberta na sequência: matar só o processo `nest start --watch` não basta — em modo watch, o binário compilado roda como um processo **filho** separado (`node ... apps/api/dist/main`), que sobrevive se for morto na ordem errada ou se uma janela/terminal for fechada sem parar a árvore inteira. Sempre conferir `netstat -ano | grep :3001` (ou listar processos `node.exe` e olhar a `CommandLine` de cada um) antes de assumir que "a API está parada".

## Fase 46 — Proteção de rota via SSR (`middleware.ts`) no painel do tenant — STATUS: concluída (estendida na Fase 49 aos painéis Master e Afiliado)

## Fase 48 — Conexão WhatsApp "não oficial" real (Baileys) — STATUS: concluída

Débito registrado desde a Fase 4: a modalidade "não oficial" usava só o `FakeUnofficialProvider`, um simulador em memória — nunca ganhou uma ponte de verdade. A pedido explícito do usuário, esta fase substitui o simulador (mantido como opção, ver abaixo) por uma implementação real via `@whiskeysockets/baileys` (protocolo multi-device do WhatsApp Web, mesma família de bibliotecas usada por projetos como Evolution API) — QR Code real, sessão persistida em disco, mensagens de entrada/saída de verdade.

- **Interop ESM em projeto CommonJS**: `@whiskeysockets/baileys` é publicado só como ESM (`"type": "module"`), mas `apps/api` compila para CommonJS. TypeScript reescreve `await import(...)` para `require(...)` sob esse alvo — o que quebra em runtime com `ERR_REQUIRE_ESM` para um pacote ESM puro (confirmado com um teste isolado antes de construir o resto da integração em cima). `apps/api/src/whatsapp/providers/baileys/baileys-esm.loader.ts` usa `new Function("specifier", "return import(specifier)")` para preservar o `import()` nativo do Node — workaround reconhecido pelos próprios mantenedores do TypeScript para este caso (microsoft/TypeScript#43329), isolado num único arquivo pequeno atrás de `BaileysLoaderService` (facilita trocar por mock nos testes, ver abaixo).
- **`BaileysConnectionManagerService`** (novo): dono do ciclo de vida de todos os sockets Baileys ativos do processo — um WebSocket persistente por número, mesmo padrão de estado em memória do `RealtimeGateway`. `useMultiFileAuthState` persiste as credenciais de pareamento em disco (`WHATSAPP_SESSIONS_DIR`, um `.env` novo, por padrão `.baileys-sessions/<numberId>/`, git-ignorado). Reconexão automática (sem novo QR) quando a conexão cai por instabilidade de rede; só exige escanear de novo em logout explícito (`disconnect()`) ou quando o WhatsApp desloga o aparelho remotamente (`DisconnectReason.loggedOut`).
- **`BaileysUnofficialProvider`** (novo): traduz o contrato `WhatsAppProvider` já existente (mesma interface do `MetaOfficialProvider`/`FakeUnofficialProvider`) para chamadas no connection manager — nenhum outro módulo do sistema precisou mudar para saber que agora há uma ponte real.
- **Mensagens recebidas pelo socket**: como não há webhook HTTP nesse modelo (é um socket persistente, não um POST de terceiro), `BaileysConnectionManagerService` emite um evento interno (`whatsapp.baileys.incoming_message`) capturado por `BaileysIncomingListener` (novo, vive no `WhatsappModule` para não criar import circular entre `ProvidersModule` e o módulo de conversas) — que resolve o contexto de tenant (`tenantContextStorage.run`) e chama `ConversationsService.handleIncoming`, exatamente o mesmo ponto de entrada usado pelo webhook real da Meta.
- **QR Code de verdade na tela, finalmente**: descobri navegando o código que o frontend nunca renderizava o `qrCode` retornado por `connect()` como imagem — ficava um campo morto na resposta da API. `NumbersService` agora usa `qrcode` (npm) para converter o QR cru em uma imagem PNG (`data:image/png;base64,...`) antes de devolver ao frontend, e `apps/web/src/app/painel/whatsapp/page.tsx` ganhou um painel com `<img>` de verdade — corrige um gap real de UX que não era específico do Baileys (afetava o simulador antigo também).
- **Polling do QR ao vivo**: diferente do simulador (QR fixo até confirmar manualmente), o Baileys real troca o QR sozinho a cada ~20s até ser escaneado. Novo endpoint `GET /whatsapp/numbers/:id/qr` + hook `useNumberQr` (frontend, `refetchInterval` de 3s enquanto `status !== "connected"`) substituem o antigo botão "confirmar conexão" para este provedor — que continua existindo só para `fake_unofficial`, onde a confirmação é mesmo manual.
- **Seleção de provedor por env** (mesmo padrão do `PaymentProvider` da Fase 17): `WHATSAPP_UNOFFICIAL_PROVIDER` — `baileys_unofficial` por padrão em `.env.example` (ponte real), mas mantido como `fake_unofficial` no `.env` deste ambiente de desenvolvimento (documentado no próprio arquivo): a suíte automatizada e este ambiente não têm um telefone real disponível para escanear um QR de verdade, e abrir um socket real contra os servidores do WhatsApp durante os testes seria lento, dependente de rede e simplesmente não teria o que confirmar do outro lado.
- **Testes** (`apps/api/src/test/whatsapp-baileys.spec.ts`, 4 casos novos): como não é viável abrir um socket real num teste automatizado, `BaileysLoaderService` é substituído (`overrideProvider`) por um dublê fiel ao formato real (`default()`/`ev.on()`/eventos `connection.update`/`messages.upsert`) — permite exercitar o fluxo completo (QR → conexão aberta → mensagem recebida chegando na conversa pelo mesmo pipeline do webhook da Meta → envio de mensagem chamando `sock.sendMessage` → logout chamando `sock.logout` e exigindo novo QR) sem rede. O teste pré-existente de Fase 4 (`whatsapp.spec.ts`) foi ajustado — não porque quebrou, mas porque a asserção antiga (`qrCode` contém `"fake-qr:"`) checava o formato antigo, pré-renderização como imagem; passou a checar o novo formato (`data:image/png;base64,...`), que agora vale para os dois provedores. 146/146 testes passando (142 anteriores + 4 novos): a suíte completa reportou 2 suítes com `PrismaClientInitializationError` ("Can't reach database server") numa execução sequencial de 13 minutos — reexecutadas isoladamente logo em seguida, ambas passaram (5/5 testes), confirmando flutuação transitória de conexão com o Postgres sob a execução longa, não uma regressão; nenhuma delas toca WhatsApp/Baileys.
- **Verificação em navegador**: bloqueada pelo mesmo problema de ambiente já documentado na Fase 46 (Node v24 / `ts-node` impedindo `nest start --watch` de subir) — não é uma limitação nova desta fase. A cobertura real do protocolo do WhatsApp em si (o que acontece de fato entre o Baileys e os servidores do WhatsApp) depende necessariamente de um telefone real escaneando um QR de verdade, algo que só o usuário pode fazer — nenhum ambiente automatizado consegue simular essa ponta.

Débito técnico consciente, registrado deliberadamente: reconexão automática ao reiniciar o processo (restart frio) não está implementada — a sessão em disco continua válida, mas o processo não tenta reabrir sozinho os sockets das conexões que estavam `connected` antes de cair; hoje isso exige um novo `connect()` manual (que reaproveita a sessão salva, sem pedir QR novo, contanto que o processo não tenha ficado offline tempo suficiente para o WhatsApp invalidar a sessão do lado dele). Mídia recebida (imagem/áudio/documento) sem legenda/transcrição de texto é ignorada silenciosamente pelo listener de mensagens — só texto é processado nesta fase, mesmo nível de esforço do `MetaOfficialProvider` existente.

## Deploy-prep — Preparação para deploy em VPS — STATUS: concluída

A pedido explícito do usuário ("faça o que falta para ficar pronto pra subir na vps"), depois de uma avaliação honesta anterior de que a plataforma ainda não estava pronta para deploy real. Diferente das fases de funcionalidade, aqui o trabalho foi maioritariamente infraestrutura + depuração: cada Dockerfile foi de fato construído com `docker build` e testado subindo o container, não escrito às cegas — isso revelou 6 bugs reais que só se manifestavam em runtime de produção (nenhum aparecia em dev ou nos testes automatizados).

- **`docker-compose.yml`**: reescrito — variáveis de ambiente de `postgres`/`redis`/`minio` com fallback (`${VAR:-default}`); todas as portas publicadas passaram de `"PORTA:PORTA"` para `"127.0.0.1:PORTA:PORTA"` (Docker escreve suas próprias regras de `iptables` que ignoram o `ufw` — publicar em `0.0.0.0` expõe o serviço na internet mesmo com firewall configurado); serviços `api`/`web` ganharam labels do Traefik (roteamento por `Host()`, TLS via `certresolver=le`); Traefik ganhou redirecionamento HTTP→HTTPS e configuração ACME/Let's Encrypt (`--certificatesresolvers.le.acme...`, desafio HTTP-01).
- **`.env.example`**: novas seções — `NEXT_PUBLIC_API_URL` (build-time do Next.js, não runtime — precisa ir como `build.args` no compose), `APP_DOMAIN`/`API_DOMAIN`/`ACME_EMAIL` (Traefik/produção), `POSTGRES_PASSWORD`, `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD`.
- **`.dockerignore`** (novo — não existia antes): exclui `node_modules`, `dist`, `.next`, `.git`, sessões do Baileys, `.env*`. Sem ele, os Dockerfiles anteriores copiavam `node_modules` do host para dentro da imagem Linux — incluindo binários nativos compilados para Windows, um bug latente que nunca tinha sido notado por nunca terem sido testados de verdade.
- **Dockerfiles multi-stage** (`apps/api`, `apps/worker`, `apps/web`) — estágio de build com o monorepo inteiro compilando via `pnpm --filter <pkg>... build`, estágio final enxuto via `pnpm deploy --prod` (api/worker) ou saída `standalone` do Next.js (web). Os 6 bugs reais encontrados testando cada imagem de verdade (`docker build` + `docker run`), na ordem em que apareceram:
  1. **Enumeração de `package.json` incompleta**: a primeira tentativa copiava só os `package.json` de cada pacote do workspace individualmente (para cache de camada) e esqueceu `packages/tsconfig`/`packages/eslint-config`, quebrando a resolução de `devDependencies` `workspace:*` silenciosamente. Resolvido trocando por `COPY . .` do monorepo inteiro (com o novo `.dockerignore` controlando o que realmente entra).
  2. **`git` ausente para a dependência git do Baileys**: `pnpm deploy --prod` falhava resolvendo `libsignal-node` (dependência do `@whiskeysockets/baileys`, instalada via URL git, não um pacote npm comum) porque `node:20-alpine` não tem `git` por padrão. Resolvido com `apk add git` no estágio de build de `apps/api`.
  3. **`packages/database`/`packages/validation` sem build real**: `main`/`types` apontavam para o `.ts` cru — funcionava em dev (ts-node/Next transpilam na hora) mas quebrava em produção com `SyntaxError: Unexpected token 'export'` ao rodar o `node dist/main.js` compilado. Resolvido dando aos dois um `tsc` real (alvo `CommonJS`, corrigindo também o `moduleResolution` herdado como `NodeNext` do tsconfig base) via script `prepare`, que roda automaticamente em todo `pnpm install`.
  4. **Prisma Client não sobrevive ao `pnpm deploy --prod`**: o `node_modules` isolado que o `pnpm deploy` recria do zero para a imagem final não herda o client já gerado, e o `.bin/prisma` fica com link quebrado nesse `node_modules` podado. Resolvido chamando o CLI do Prisma pelo caminho real do pacote (`.pnpm/node_modules/prisma/build/index.js`), com `cwd` dentro do próprio pacote `@chatbot-saas/database` já deployado — de fora, o Prisma não localizava o `@prisma/client` local e tentava (e falhava) um `npm install` via rede.
  5. **`libssl` ausente no Alpine**: o binário do query engine do Prisma travava com `Error loading shared library libssl.so.1.1` — `node:20-alpine` moderno vem com OpenSSL 3.x, não 1.1.x. Resolvido com `binaryTargets = ["native", "linux-musl-openssl-3.0.x"]` explícito em `packages/database/prisma/schema.prisma` e `apk add openssl` (necessário também para a própria detecção de versão do Prisma funcionar) nos estágios de build e runtime de `api`/`worker`.
  6. **`/cadastro` quebrando o build do Next.js**: `useSearchParams()` sem `<Suspense>` ao redor quebra a exportação estática em produção (`Export encountered errors... /cadastro`) — nunca aparecia em dev. Resolvido envolvendo o formulário num `<Suspense>`.

### Deploy real na VPS do usuário — bugs adicionais encontrados e corrigidos

Diferente do trabalho acima (testado localmente, nunca contra um servidor real), esta parte aconteceu numa VPS real do usuário, com acompanhamento passo a passo via SSH — revelou mais 4 bugs reais que só apareciam nesse contexto (nenhum visível em `docker build`/`docker run` local):

- **`pnpm`/`ts-node` não existem na imagem de produção**: o `DEPLOY.md` original instruía `docker compose run --rm api pnpm --filter database migrate:deploy`/`... seed` — mas a imagem final do `api` (via `pnpm deploy --prod`) não tem `pnpm` funcional nem `ts-node` disponível, só o necessário para `node dist/main.js`. Corrigido chamando o Prisma CLI e o `seed.js` compilado diretamente via `node`, mesmo padrão já usado para o `prisma generate` no Dockerfile (ver bug 4 acima) — comandos atualizados no `DEPLOY.md`.
- **Colisão de nomes entre projetos na mesma rede Docker**: a VPS já tinha outro projeto (`agendamento-barbearias`) com a stack inteira (`postgres`/`redis`/`minio`/Traefik) numa única rede Docker. Conectar nossos `api`/`web` nessa mesma rede (necessário para o Traefik existente rotear pra gente) fazia o DNS interno do Docker resolver `postgres`/`redis`/`minio` ambiguamente — às vezes batendo no container certo, às vezes no do outro projeto. Sintoma real: erro de autenticação do Postgres com uma senha que, testada manualmente, estava correta — só que contra o banco errado. Corrigido criando uma rede pequena e exclusiva (`docker-compose.traefik-shared.yml`), só com nosso `api`/`web` e o Traefik existente conectado manualmente a ela — nunca entrando na rede do outro projeto inteira.
- **Nomes de router do Traefik colidindo entre projetos**: o Traefik nomeia rotas globalmente pelo nome literal do label (`traefik.http.routers.api...`), não por projeto — como o outro projeto também tinha serviços chamados `api`/`web`, os nomes colidiam (`HTTP router defined multiple times with different configurations`) e nenhuma configuração era aplicada de forma confiável. Corrigido prefixando os nomes (`chatbot-saas-api`/`chatbot-saas-web`).
- **504 Gateway Timeout com container em duas redes**: mesmo depois dos dois bugs acima corrigidos, `api`/`web` respondiam 504 através do domínio — apesar de TLS completar, nenhum erro nos logs do Traefik, e conectividade direta confirmada (`docker exec <traefik> wget <ip-do-container>` funcionando). Causa: com o container em duas redes (a nossa + a rede-ponte do Traefik), o Traefik não sabe sozinho qual delas usar para alcançar o container, e escolhe uma silenciosamente — sem logar erro nenhum quando escolhe errado. Corrigido com o label `traefik.docker.network` apontando explicitamente para a rede-ponte.

Também descoberto nesse processo, sem solução aplicada (fora do nosso controle — token de terceiro, não código do repositório): o Traefik existente usa desafio DNS-01 via Cloudflare para emitir certificados, e o token de API configurado não está conseguindo criar o registro TXT de verificação (`_acme-challenge...`) — confirmado que o problema é pré-existente e afeta também o domínio do outro projeto, não é causado por nós. Certificado servido hoje é o autoassinado padrão do Traefik; a plataforma responde `200` corretamente via HTTPS com `curl -k` (ignorando validação do certificado) nos dois domínios (`chatbot.agenciaclamber.com.br` e `api.chatbot.agenciaclamber.com.br`). Resolver isso exige acesso ao dashboard da Cloudflare (permissão do token) — decisão consciente do usuário de deixar para depois e seguir testando por ora.

- **`docker-compose.traefik-shared.yml` e `.env.example`**: documentados com o passo a passo completo de descoberta desses valores (rede, certresolver) e os avisos sobre os dois bugs de colisão, para qualquer deploy futuro em VPS compartilhada.

## Fase 7 — Automação — STATUS: concluída

Implementado e testado (53 testes automatizados passando, incluindo os 6 de Fase 7 — cobrindo os casos críticos #8 "automação não executa duas vezes indevidamente" e #9 "follow-up é cancelado após resposta"). Peça central nova: um barramento de eventos de domínio real (`@nestjs/event-emitter`, `DomainEventsService` global) — os módulos existentes (WhatsApp, CRM, Chatbot, Atendimento) apenas emitem eventos tipados (`conversation.created`, `message.received`, `opportunity.stage_changed`, `opportunity.won`, `opportunity.lost`, `crm_task.created`, `chatbot.flow.completed`, `chatbot.flow.abandoned`, `chatbot.flow.transferred`) sem saber que a Automação existe — dependência é sempre de fora para dentro (WhatsApp/CRM/Atendimento → Automação → Providers/Realtime/Chatbot), sem ciclo.

- **Motor de automação via fila real** (BullMQ, fila `automations`): `AutomationEngineService` escuta os eventos, casa `Automation` ativas por `tenantId`+`gatilhoTipo`, avalia `condicoes` (campo/operador/valor sobre o payload do evento) e, se bater, cria um `AutomationExecution` (`status: pending`) **antes** de enfileirar — essa linha no banco é a âncora de idempotência. `AutomationProducer` enfileira com `jobId` derivado do `executionId`, dedup estrutural do próprio BullMQ; `AutomationProcessor` reforça a idempotência checando `status !== 'success' && status !== 'dead_letter'` antes de processar (permite retry de job `pending`/`failed` mas nunca reexecuta uma execução já finalizada) — testado enfileirando manualmente a mesma execução já concluída e confirmando que a ação (criação de tarefa) não repete.
- **9 tipos de ação reais**: enviar mensagem, criar tarefa, aplicar/remover tag, atualizar campo, mover oportunidade de etapa, iniciar chatbot, disparar webhook, agendar follow-up — cada uma checando dependências (ex.: `contactId`/`conversationId` presentes) e retornando `skipped` em vez de estourar erro quando a ação não se aplica ao contexto do evento.
- **Retry/backoff/dead-letter reais**: 3 tentativas com backoff exponencial (5s/10s/20s); na última tentativa falha, `AutomationExecution.status` vira `dead_letter` (em vez de ficar reprocessando para sempre); testado forçando uma violação de FK real (mover para etapa inexistente) e confirmando a transição para `failed` já na primeira tentativa.
- **Follow-ups agendados com cancelamento automático**: `FollowUpsService.schedule()` cria `FollowUpSchedule` + job BullMQ atrasado (`delay`); cancelamento é "cinto e suspensório" — marca a linha como `cancelled` no banco E tenta remover o job da fila. Ligado automaticamente em três pontos reais: resposta do cliente (`ConversationsService.handleIncoming` → `customer_replied`), encerramento de conversa (`InboxService.close` → `conversation_closed`), oportunidade ganha/perdida (`OpportunitiesService.close` → `opportunity_won`/`opportunity_lost`). Testado ponta a ponta: agendar follow-up por automação, responder como cliente antes do disparo, confirmar `status: cancelled` e que a mensagem de follow-up nunca chega à conversa.

Débito técnico consciente, registrado deliberadamente: só 9 dos ~16 gatilhos documentados no prompt mestre estão ligados a eventos de domínio reais nesta fase (os demais exigem funcionalidades que ainda não existem, ex. campanhas, prazos de SLA); `send_webhook` não tem assinatura HMAC nem um modelo `WebhookEndpoint` dedicado ainda (usa a URL informada diretamente na ação); `move_opportunity_stage` escolhe a oportunidade aberta mais recente do contato, não uma específica (não há como referenciar uma oportunidade por evento genérico ainda); o processamento roda dentro de `apps/api` (não em `apps/worker` separado) porque as ações reutilizam serviços que já vivem aqui (provider WhatsApp, engine do Chatbot) — extrair isso para um pacote compartilhado não se justifica nesta fase.

- Recuperação de senha com token de uso único e resposta neutra.
- Rate limiting básico em login/recuperação.
- Critério de pronto: casos de teste críticos #2 (autorização) e itens de `SECURITY.md` §1 cobertos por teste automatizado.

### 1.4 Multiempresa
- Middleware/guard de resolução de tenant (JWT claim; preparar também resolução por subdomínio para uso futuro em Domains).
- Wrapper de acesso a dados que injeta `tenantId` automaticamente nas entidades multiempresa.
- Critério de pronto: caso de teste crítico #1 (isolamento de tenant) implementado e passando, cobrindo pelo menos controllers, services e uma fila de exemplo.

### 1.5 Usuários e permissões
- CRUD de `TenantUser` (convite, ativação, inativação, remoção, troca de papel).
- Modelo RBAC inicial (`Role`, `Permission`) com os papéis padrão de `PERMISSIONS_MATRIX.md` §2–3 — mesmo sem os módulos comerciais implementados ainda, a estrutura de permissão já existe e é testável.
- Guard de permissão reutilizável (`@RequirePermission`).
- Critério de pronto: teste cobrindo usuário sem permissão recebendo 403.

### 1.6 Auditoria
- Serviço central de auditoria (`AuditLog`) com interceptor/decorator reutilizável.
- Cobertura inicial: login, logout, recuperação de senha, criação/edição/remoção de `TenantUser`, mudança de `Role`/`Permission`.
- Critério de pronto: cada ação da lista acima gera exatamente um registro de auditoria coerente.

### 1.7 Arquivos
- Integração com storage S3-compatible (MinIO em dev), upload com URL assinada, bucket privado.
- Critério de pronto: upload/download funcional respeitando isolamento de tenant no prefixo da chave.

### 1.8 Filas e feature flags
- BullMQ configurado com ao menos uma fila de exemplo funcional (ex.: fila de notificação) para validar a infraestrutura de filas ponta a ponta.
- Modelo `FeatureFlag` funcional com endpoint `GET /tenants/me/features` (ainda sem módulos comerciais reais por trás, mas a infraestrutura de flag está pronta para a Fase 2+).
- Critério de pronto: job de exemplo publicado, processado pelo worker e resultado auditável.

### 1.9 Testes fundamentais
- Suíte de testes de isolamento multi-tenant (caso crítico #1) rodando em CI local.
- Suíte de testes de autorização (caso crítico #2).
- Testes unitários de hashing/token/rotação de refresh token.

### Ordem de execução recomendada dentro da Fase 1
1.1 → 1.2 → 1.3 → 1.4 → 1.5 → 1.6 → (1.7 e 1.8 em paralelo, são independentes entre si) → 1.9.

### Riscos identificados para a Fase 1
- Definição do mecanismo exato de resolução de tenant por subdomínio pode exigir decisão de infraestrutura (Traefik roteando por Host header) antes de codar — validar em `ARCHITECTURE.md` durante a implementação, não travar a fase por isso (fallback: resolução só por JWT claim nesta fase, subdomínio entra na Fase 2/Domains).
- Row-Level Security do Postgres (`SECURITY.md` §2) é decisão de custo/benefício — avaliar na Fase 1 se entra já ou fica registrada como débito técnico consciente para a Fase 10 (Estabilização).
- Seed do `MasterUser` inicial precisa de mecanismo seguro (senha gerada ou lida de variável de ambiente obrigatória) para não deixar credencial padrão previsível em produção.

## Fases 2–10 (visão resumida, detalhamento em ciclo próprio antes de cada início de fase)

Cada fase, ao ser iniciada, deve repetir o processo da seção 30 do prompt mestre: analisar o projeto existente, documentar o que será desenvolvido, listar migrations necessárias, listar riscos, identificar dependências, criar plano pequeno e verificável, implementar em etapas, testar, corrigir, atualizar documentação.

- **Fase 2** depende de 1.4/1.5 (multiempresa + permissões) prontos — painel Master é, na prática, o `MasterUser` operando sobre `Tenant`/`Plan`/`Subscription`.
- **Fase 3 (CRM)** depende de 1.4/1.6 (multiempresa + auditoria) — é o primeiro módulo comercial real, valida a infraestrutura de `FeatureFlag` da Fase 1.9 em uso real.
- **Fase 4 (WhatsApp)** depende de 1.8 (filas) e da abstração de provedor definida em `ARCHITECTURE.md` §6 — é pré-requisito de Atendimento, Chatbot (execução) e Automação (envio).
- **Fase 5 (Atendimento)** depende de Fase 3 (CRM, para vínculo de contato) e Fase 4 (WhatsApp, para canal real).
- **Fase 6 (Chatbot)** depende de Fase 4 e se integra com Fase 3 conforme `MODULE_DEPENDENCIES.md`.
- **Fase 7 (Automação)** depende de Fases 3–6 existirem (é o módulo mais "consumidor" de eventos dos demais).
- **Fase 8 (Financeiro/Afiliados)** pode iniciar em paralelo à Fase 3–7 do ponto de vista técnico, mas depende de Fase 2 (planos/assinaturas) estar madura.
- **Fase 9 (Relatórios)** consolida dados de todas as fases anteriores — naturalmente uma das últimas a fechar por completo.
- **Fase 10 (Estabilização)** revisita todos os débitos técnicos conscientes registrados ao longo das fases anteriores (ex.: RLS adiado na Fase 1).
